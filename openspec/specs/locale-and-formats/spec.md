# Locale and Formats Specification

## Purpose

Define how the system resolves its display locale and derives number and
date/time formats from it, so that the business default locale is the single
source of truth for language and formatting, with a defined extension point for
future languages.

## Requirements

### Requirement: Single business locale

The system MUST resolve exactly one display locale for the whole business from
`BusinessSettings.default_locale` (persisted values `es` and `en`). Individual
users MUST NOT be able to override the display locale; there MUST be no
per-user locale preference in `localStorage` or in the database.

#### Scenario: No per-user switch

- GIVEN the user opens User Settings
- WHEN they inspect the available preferences
- THEN no language selector is offered

### Requirement: Formats derived from the locale

The system MUST derive number formatting and date/time formatting from the
resolved locale (`es` → `es-AR`, `en` → `en-US`) and MUST NOT keep an
independent number-format setting. The `number_format` field MUST NOT exist in
`BusinessSettings`, its API schemas, or the autogenerated client.

#### Scenario: Locale drives number formatting

- GIVEN the business `default_locale` is `es`
- WHEN a money amount of 1234.5 is rendered anywhere in the UI
- THEN it displays with `es-AR` conventions (e.g. `1.234,50`)

#### Scenario: Locale drives date and time formatting

- GIVEN the business `default_locale` is `en` and the business timezone is set
- WHEN a document date or a session timestamp is rendered in the UI
- THEN it is formatted with `en-US` conventions through the centralized date
  helpers, in the business timezone

### Requirement: Centralized formatting helpers

All number, money, date, and time rendering MUST go through the shared
formatting helpers (`frontend/src/lib/format.ts` and `datePresets.ts`), which
take the resolved locale from the i18n context. Components MUST NOT hardcode
locale tags (`es-AR`, `en-US`) in formatting calls and MUST NOT receive
`numberFormat` props.

#### Scenario: No scattered formatting

- GIVEN the frontend source tree
- WHEN searching for `toLocaleDateString("es-AR")`, bare `toLocaleString()`
  date rendering in components, or `numberFormat` props
- THEN no component-level matches exist outside the shared helpers

### Requirement: Locale change propagation

When an administrator changes `default_locale` in Admin → General, the change
MUST persist via the business-settings API, and every subsequently loaded
screen MUST render language, numbers, and dates according to the new locale.

#### Scenario: Administrator switches the business locale

- GIVEN the business `default_locale` is `es`
- WHEN the administrator changes it to `en` and reloads
- THEN all labels, numbers, and dates render with `en-US` conventions

### Requirement: Extensible locale enumeration

Adding a future language MUST require only: one new react-intl message
catalog, one new `LocalePreference` enum value on the backend, and one
locale-tag mapping entry in the frontend. No architectural change (state
management, format plumbing, settings schema) MUST be required.

#### Scenario: Catalog-driven growth

- GIVEN the current implementation
- WHEN a third language is added per the list above
- THEN all UI text, numbers, and dates follow the new locale without further
  code changes to components
