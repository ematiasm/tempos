# Design: Move Project Law into OpenSpec Specs

## Context

`AGENTS.md` is the only always-on channel: the harness injects it into every prompt,
while `openspec/config.yaml` and `openspec/specs/**` are read on demand. That asymmetry
is exactly why the file grew into a second, unverified spec store — and why deleting it
outright was rejected: the four transactional invariants would stop reaching inline and
delegated work, which is most of the work in this repository.

The design therefore keeps a small always-on file and turns it into a **pointer index**:
every prompt still names the file that owns each invariant, while the contract itself
lives where `sdd-verify` can check it.

## Decisions

### D-A. Enforcement over prose (trigger instead of discipline)

Verified before deciding: no migration contains `TRIGGER`, `REVOKE` or `GRANT`; no test
protects ledger immutability; no code path in `backend/app` issues `UPDATE`/`DELETE`
against the four ledger tables today. The invariant is therefore upheld by discipline
only — the same exposure that let `d61ddf38636a` drop two database invariants and go
unnoticed for eleven revisions.

Grants were rejected because `backup.py:restore_database` restores with
`pg_restore --no-owner --no-privileges`: object privileges do not survive a restore, so
the guard would silently vanish on the first disaster recovery.

**Mechanism.** One hand-written migration creates a single `plpgsql` function and
attaches a `BEFORE UPDATE OR DELETE ... FOR EACH ROW` trigger to each protected table.
The migration follows the house style already established by `39c9148ae5e4`:

- `CREATE OR REPLACE FUNCTION` so a partially applied environment converges;
- `DROP TRIGGER IF EXISTS` before each `CREATE TRIGGER`, so re-running is safe;
- an explicit `downgrade()` that drops the triggers and the function, touching no data;
- no business data is read or written by the migration in either direction.

Protected tables (five): `StockMovement`, `AccountMovement`,
`CustomerAccountMovement`, `SupplierAccountMovement`, `Transfer`. `Transfer` has no
mutation path in the API today, so the guard only formalises what is already true.

### D-B. The cleanup disables user triggers for its own transaction

`backend/tests/conftest.py` lists those five tables in `CLEANUP_MODELS` and
`_clean_test_data` issues a `DELETE` after every test, so a `DELETE` trigger would
fail the whole suite. The cleanup therefore keeps its current
`DELETE ... WHERE pk NOT IN baseline` and wraps it in
`SET LOCAL session_replication_role = replica`.

`TRUNCATE` was the first choice and was measured out of it: the fixture's contract is
that rows which existed when the session started are preserved, and the dev database
currently holds 17 real ledger rows (6 stock movements, 7 account movements, 1 customer
movement, 2 supplier movements, 1 transfer) whose 6 documents and 18 products would
survive. `TRUNCATE` ignores the per-row baseline and would delete them, leaving
documents without movements and `stock_current` / `saldo` caches detached from the
ledger behind them.

`session_replication_role` needs superuser (the test suite connects as `postgres`, the
compose owner) and is transaction-scoped: the cleanup commit clears it before `init_db`
runs. A side effect worth knowing: it also disables foreign-key triggers in that
transaction, so cleanup no longer depends on the children-before-parents ordering.

This is a deliberate, narrow bypass, not a hatch in the guard: the guard itself has no
condition, and no application path can reach the setting without superuser access.

### D-C. The guard ships with a presence test

`backend/app/alembic/env.py` declares no custom comparators, and autogenerate does not
reflect triggers. `check-schema.sh` (`alembic check`) therefore **cannot** protect this
guard — this is the one invariant in the repository that the schema gate is blind to,
by construction. That is precisely the failure mode of `d61ddf38636a`, where two objects
that lived only in migrations became invisible.

Consequence: the slice must ship

1. a behaviour test that attempts an `UPDATE` and a `DELETE` and asserts the database
   raises while the row is unchanged, and
2. a presence test that queries `pg_trigger` for the five tables.

Without (2) the guard is one autogenerated migration away from silent removal.

### D-D. The index keeps pointers, not summaries

The contradiction at `AGENTS.md:389` (`precio_venta` "carries IVA inside") against
`pricing/spec.md` is the evidence: a summary maintained beside a spec rots, and nothing
catches it. The index therefore names the owning file and never restates the rule.

Target shape of `AGENTS.md` (~50 lines):

```text
# tempos — Agent Guide

Purpose (2-3 lines) + pointer: "behaviour lives in openspec/specs/"

## Where the rules live
- transactional invariants -> openspec/specs/transactional-integrity/spec.md
- document lifecycle      -> openspec/specs/documents/spec.md
- catalog / counterparties / cash sessions -> their specs
- layout, stack, conventions -> docs/ARCHITECTURE.md
- testing gotchas          -> docs/TESTING.md

## Working rules (7)
1  Do not invent business data — ask first
2  New SQL table -> Alembic migration; model and migration land together,
   and the generated migration is read before it is applied
3  OpenAPI shape change -> regenerate the client, then typecheck
4  Gates: always <names>; conditional <names>   (commands in openspec/config.yaml)
5  Pagination through Page[T] + PaginationDep
6  New permission -> add it to the init_db seed
7  Auth dependency: require_permissions for granular, superuser dep otherwise

## Reserved
cae/cae_vto nullable, mono-store schema — owned by documents spec
```

### D-H. Conciliation becomes an append-only log

The guard's first full-suite run failed on a shipped feature:
`api/routes/account_movements.py` set `movement.conciliado = True`, producing
`UPDATE accountmovement SET conciliado=...`, which the trigger rejected with
`RestrictViolation`. The route's own docstring already stated the intent — "only the
conciliation flag is touched; the ledger amount and direction remain immutable" — which
is exactly the split the guard could not express.

Two ways out, decided by the user: carve the flag out of the guard, or stop mutating
the ledger. **The log wins.** `conciliation` holds one row per conciliated movement
(`account_movement_id` unique, `user_id`, `conciliated_at`), the backfill attributes
existing rows to the movement's user and creation time — the only provenance the old
boolean left — and the table joins the guard. `AccountMovementPublic.conciliado` is
derived in `_decorate`, so the OpenAPI shape is unchanged and no client change is
needed. The list filter switches from a column comparison to `IN (SELECT ...)`.

This is the clearest evidence of what the change is worth: a shipped feature had been
writing to a ledger that was documented as immutable, and nothing noticed until an
trigger said so.

### D-I. Test-only escape hatches are explicit helpers

Two test paths needed to write to a guarded table: the cleanup (deleting test rows) and
one test pinning a movement's `created_at` for a business-day assertion. Both use
`SET LOCAL session_replication_role = replica` inside a helper (`_clean_test_data` and
`tests/utils/ledger.py: pin_created_at`) rather than an inline escape, so the bypass is
named, superuser-only and reviewable. The guard itself carries no condition.

### D-E. Documentation split

Non-behavioural content leaves the index entirely:

- `docs/ARCHITECTURE.md`: where things live (backend + frontend + root), stack and
  conventions, the rationale of the database invariants, migration traps
  (`postgresql.ENUM(..., create_type=False)`), the custom `ThemeProvider`, the
  `ENVIRONMENT=local` private router, that Backups come from the upstream template.
- `docs/TESTING.md`: the real-Postgres autouse fixture, the non-parallel caveat, the
  cash-session rule after D-F, the PEP 758 lint trap, `uv run bash scripts/...`, the
  Playwright requirements and the disk-prune note.

Commands keep a single source: `openspec/config.yaml: testing`. The index names gates,
never commands (D3 in the proposal).

### D-F. The orphaned session is fixed where it is caused

The autouse `open_cash_session` fixture currently fails the whole suite when a stray
`OPEN` session exists, which forces a manual `UPDATE` or a destructive
`docker compose down -v` on a dev database. The fixture will close the stray session and
continue; the known-issues entry disappears instead of being documented.

### D-G. `config.yaml` citations move with the rules

Three live citations must not dangle:

| Current | Becomes |
|---|---|
| `rules.proposal`: "AGENTS.md rule 1" | unchanged — rule 1 stays rule 1 in the index |
| `rules.design`: "AGENTS.md rules 5-7, 15" | `openspec/specs/transactional-integrity/spec.md` |
| `rules.apply`: "AGENTS.md section 4" | `docs/ARCHITECTURE.md` |

## Delivery

Five stacked PRs against `main` (squash-merge only per the Protect main ruleset), in
this order, each with its own issue:

| PR | Contents | Boundary |
|---|---|---|
| 1 | change artifacts (proposal, design, tasks) + `transactional-integrity` spec + trigger migration + `pg_trigger` test + behaviour test + cleanup change + the conciliation log | the only PR with runtime risk (a table, a dropped column and a trigger); reverting runs both migrations' `downgrade` |
| 2 | `documents`, `catalog`, `counterparties`, `cash-sessions` specs + `payments` ADDED + the two `REMOVED` deltas | documentation only; no runtime effect |
| 3 | `docs/ARCHITECTURE.md`, `docs/TESTING.md`, cash-session fixture fix, two orphan files deleted | no contract change |
| 4 | `AGENTS.md`: §6 and §8 removed, `config.yaml` citations updated | deletions only, behaviour unchanged |
| 5 | `AGENTS.md`: §3 and §4 removed, §1/§2/§5 rewritten as the index | closes the change |

PR 1 and PR 3 both touch `backend/tests/conftest.py` (cleanup vs fixture) in different
functions; PR 3 must branch from `main` after PR 1 merges.

Canonical spec sync and archive happen after PR 2 is merged and verified: the deltas
under `openspec/changes/move-project-law-to-specs/specs/` are the source, and
`sdd-sync` merges them into `openspec/specs/`.

## Verification

- `bash backend/scripts/test.sh` — includes the new behaviour and presence tests.
- `bash backend/scripts/lint.sh` and `bash backend/scripts/check-schema.sh`.
- `cd frontend && bunx tsc -p tsconfig.build.json --noEmit && bun run lint` — the dead
  component removal must not break the build.
- A consistency check that no live file still cites `AGENTS.md` for a contract that
  moved, and that the index contains no behavioural contract owned by a spec.
