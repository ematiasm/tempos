# Proposal: Refine Sell Counter Screen

## Intent

tempos replaces Aronium at a retail counter, but `/sell` is not daily-counter grade yet: barcode scans can resolve to the wrong product (name ordering wins over exact barcode), variant barcodes are invisible to search, fractioned goods (kg/gram) cannot be sold, payment supports a single method, the post-sale flow cannot produce a proper voucher (80mm/A4/email/PDF/note), and selling neither requires nor tags an open cash session — so the arqueo is blind to counter sales. This change makes `/sell` fast and reliable for barcode-scanner daily use.

## Scope

### In Scope
1. **Search/barcode**: ↑/↓ + Enter suggestion navigation; exact barcode matches rank above name matches; variant barcodes searchable (backend).
2. **Fractioned products** (decimal UoM): quantity-entry modal instead of auto qty 1.
3. **Payments**: one quick button per payment method (instant confirm; `marks_paid=false` credit methods force customer selection) + split-payment dialog (N methods × amounts; credit portion requires customer).
4. **Post-sale window**: sale details + vuelto; print 80mm thermal / A4; send by email (auto if customer has email, else prompt); save PDF; add note; new-sale reset.
5. **Cash gating**: selling requires an open cash session; sales send `Document.cash_session_id` (backend field exists).
6. **Admin "Printing" section**: default format (80mm/A4) + voucher header/footer/legends — new `BusinessSettings` fields + Alembic migration.

### Out of Scope
- Multi-store / multi-warehouse (AGENTS.md §7).
- AFIP/ARCA electronic invoicing (`cae` fields stay reserved).
- ESC/POS direct printing and printer-device preselection (deferred; browsers cannot preselect printers — user accepted).
- Backend PDF-generation library (browser print-to-PDF instead).

## Capabilities

> Contract with sdd-spec. `openspec/specs/` is currently empty — all capabilities are new.

### New Capabilities
- `product-search`: suggestion navigation + barcode matching rules (exact-first, variant barcodes).
- `sell-screen`: fractioned-quantity capture, cash-session gate, `cash_session_id` tagging.
- `payments`: quick method shortcuts, split-payment dialog, credit-requires-customer rule.
- `post-sale-actions`: post-sale window, 80mm/A4 voucher printing, email, PDF, note, reset.
- `print-configuration`: BusinessSettings print defaults + admin Printing section.

### Modified Capabilities
- None.

## Approach

Frontend-heavy: decompose the 711-line `sell.tsx` into focused components (search, cart, payment, post-sale, dialogs) under `components/Sell/`. Backend stays small: reorder product search (exact barcode > exact name > partial), include `ProductVariant.barcodes`, add `BusinessSettings` print fields (migration), add a document-email endpoint reusing the existing `send_email` util (verified: none exists today — only test-email/password-recovery), and send `cash_session_id` from `/sell` (field exists; `DocumentCreate.payments` already accepts N rows). PDF via browser print-to-PDF; printing via CSS `@media print` profiles (80mm narrow vs A4). Regenerate client (`scripts/generate-client.sh`); i18n es+en; seed any new permission (e.g. `document.email`) in `init_db`.

**Size estimate**: ~1,200–1,800 authored lines across ~20–25 files (incl. tests, i18n, generated client excluded). Exceeds the 800-line single-PR budget — see Risks.

## Risks

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| Single PR exceeds 800-line budget | High | Commit-slice per capability; sdd-tasks must forecast and recommend chained PRs |
| Regressions during `sell.tsx` decomposition | Med | Mechanical extraction + Playwright E2E of critical flows |
| Split-payment vs credit-in-favor/vuelto interplay | Med | Design must reconcile with saldo/FIFO rules (AGENTS.md 5–7, 15) |
| Print CSS inconsistency across browsers | Med | Dedicated print stylesheet; verify Chromium first |
| Email blocked when SMTP unconfigured | Med | Degrade action; design decides fallback |

## Rollback Plan

Single PR: revert the PR/commit — frontend changes are additive components. Backend: `uv run alembic downgrade -1` drops only the `BusinessSettings` print columns; no ledger tables are touched (append-only integrity preserved). Client regen reverts by re-running `generate-client.sh`.

## Dependencies

- Docker stack (Postgres) up + migrations applied for tests (strict TDD, non-parallel-safe).
- SMTP configured (`emails_enabled`) for the email action; otherwise it degrades.
- No new external libraries.

## Success Criteria

- [ ] Barcode scan adds the right product/variant in one pass; exact barcode beats name matches
- [ ] ↑/↓ + Enter navigates suggestions; fractioned products open the quantity modal
- [ ] One-click sale per payment method; credit requires customer; split payments work
- [ ] Post-sale window: vuelto + 80mm/A4 print, email, PDF, note, new sale all functional
- [ ] Selling blocked without open cash session; sales carry `cash_session_id`
- [ ] Admin Printing settings persist and are honored by prints
- [ ] All AGENTS.md §4 validation gates pass; i18n complete (es/en)

## Open Questions (for spec/design)

1. Voucher content defaults (header/footer/legends): concrete default text or empty-until-configured? (AGENTS.md rule 1 — no invented business data.)
2. "Add note": persisted on `Document` (new DB field) or print-only ephemeral? Data-model decision.
3. Quick-payment buttons: map to the seeded `PaymentMethod` set? Confirm `marks_paid=false` defines "credit".
4. Split payment: does vuelto apply only to cash overpayment? Rules when the credit portion exceeds the remaining total?
5. Fractioned quantity bounds: UoM `decimals` as the only precision rule, or per-product min/max?
6. Email fallback when SMTP is disabled: hide action, `mailto:`, or store-and-forward?
